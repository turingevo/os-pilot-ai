## 4) 真实 U 盘测试（QEMU 直挂真盘）

```sh
udisksctl unmount -b /dev/sdX1 && udisksctl unmount -b /dev/sdX2   # 先卸载全部分区
sudo -E sh $AI/pack/run_qemu_usb.sh /dev/sdX                        # 需要 sudo：块设备 root:disk
```

脚本会拒绝非 USB 设备与仍挂载的设备；guest 会**真实读写** U 盘（agent 改 `ventoy.json`、写日志），
`VTOY_AI_USB_IF=usb` 可让磁盘走 QEMU 的 USB 大容量存储栈。命令行 VGA 优先时用默认 gui 窗口模式
交互；串口优先的 ISO 用 `VTOY_AI_USB_MODE=tty`。超时：第 2 参数或 `VTOY_AI_QEMU_TIMEOUT`，`0` = 不限时
（**gui 默认不限时**，tty 默认 300s）；到点是 `timeout` 发 SIGTERM（脚本会打印「被 timeout 终止
（非 guest 崩溃）」），agent 写文件是 tmp+rename 原子写且有 `.bak`，不会留下半个 `ventoy.json`。

**加一块空白靶盘手动测磁盘工具**：

```sh
# 造（或重置）空白靶盘：默认 $BUILD/test/scratch-disk.img，2 GiB，全零、无分区表
sh $AI/pack/make_blank_disk.sh [路径] [大小 MiB]

udisksctl unmount -b /dev/sdd1
VTOY_AI_SCRATCH_MB=2048 sudo -E sh $AI/pack/run_qemu_usb.sh /dev/sdd
```

- **两块盘的角色**：U 盘承载 payload，受**硬守卫**保护——对它分区/格式化的请求会被拒绝；靶盘可自由
  `partition`/`format`/`backup`。这正是装机场景：AI 能操作目标盘，动不了自己的运行环境。
- **按序列号认盘，别认设备名**：靶盘带序列号 `VTOY_AI_SCRATCH_SERIAL`（默认 `aitarget`），
  `list_disks` 会报出。`virtio` 下额外盘用 `-device` 挂载，**盘序可能变**（靶盘可能成为 `/dev/vda`）。
- **靶盘复用**：`run_qemu_usb.sh` 只在镜像缺失时创建，**不会重置**已有靶盘；要回到空白状态用
  `make_blank_disk.sh` 重建（它会覆盖同名文件）。
- **LLM**：ISO 不会改 U 盘上的 `ai.json`，它指向你既有的端点（如宿主 `192.168.3.2:8888`）；
  QEMU 走 user 网络（slirp），guest 可经宿主访问该地址。
- **别让 Ventoy 自动装机抢跑**：若 U 盘 `ventoy.json` 里已有 `auto_install` + `VTOY_DEFAULT_IMAGE`，
  开机 10 秒后会**自动进入无人值守安装并清空目标盘**。只测磁盘工具时，先去掉这两项（旁边有 `.bak`）。

实测（2026-09-28 晚，真机 U 盘 /dev/sdd + OVMF + gtk）：Ventoy 菜单选 `0-OS-PILOT-AI.iso` →
日志首行「已接管本地显示器自绘（/dev/fb0）」（**真机 UEFI GOP + simpledrm 路径成立**）→ 直连
真实模型完成 3 轮**中文**问答（本地键盘 + 内置拼音），会话日志写 U 盘 `/ventoy/ai/logs/session-*.md`。

## 7) 闭环验证：AI 建房 → 目标发行版读盘 → 真实引导

```sh
sh $AI/pack/verify_install_loop.sh   # 17 项断言全绿；免 root、免 GUI、不碰真实块设备
```

**版本对应是刻意的**：宿主自带 e2fsprogs **1.46.5** + GRUB **2.06** 与 Ubuntu 22.04 完全同版本，
即「目标发行版」的等价物；建房用随包静态 **mke2fs 1.47**（与 guest 内 AI 工具同一二进制）。两组对照：

## 8) 重装 + 修后闭环（真 U 盘 + 大靶盘）

要点：**root 给 ≥25 GiB**（太小 `update-initramfs` 写不下 → 装完没有 initrd）、**安装器沿用 AI 建好的
分区（不要重新格式化）**，这样才是在验证修好的建房路径。

```sh
# 1) 造一块 40 GiB 靶盘（稀疏；同名文件已存在会被「覆盖清空」，重建前先确认上面没有要留的证据）
sh $AI/pack/make_blank_disk.sh $BUILD/test/reinstall-target.img 40960

# 2) 卸载真实 U 盘全部分区，再启动（gui 模式在窗口里操作）
udisksctl unmount -b /dev/sdd1 && udisksctl unmount -b /dev/sdd2
VTOY_AI_SCRATCH_IMG=$BUILD/test/reinstall-target.img VTOY_AI_SCRATCH_MB=40960 \
  sudo -E sh $AI/pack/run_qemu_usb.sh /dev/sdd

# 3) guest 内：让 AI 给靶盘分区/格式化（按序列号 aitarget 认盘），root ≥25 GiB；随后在安装器里
#    选"其它选项"，把 AI 建的分区挂到 / 与 /boot/efi，**不要勾选格式化**，让安装器装引导器到 ESP。

# 4) 静态判据（全程只读，可对任意已安装镜像跑）：ESP 有引导器 / root ≥25 GiB / /boot 有 initrd 实体 /
#    ext4 无 orphan_file+metadata_csum_seed / fstab UUID 对齐；退出码 0 通过 / 1 装了但不满足启动条件 / 2 空盘
sh $AI/pack/verify_target_image.sh $BUILD/test/reinstall-target.img
#    阈值可用 VTOY_AI_TARGET_MIN_ROOT_MIB 覆盖（默认 25600 = 25 GiB）

# 5) 实地引导确认（gui 窗口里看真实启动；串口日志 $BUILD/test/qemu-target-serial.log）
sh $AI/pack/run_qemu_target.sh $BUILD/test/reinstall-target.img
#    支持 VTOY_AI_TARGET_MODE=gui|tty、VTOY_AI_TARGET_IF=virtio|ide、VTOY_AI_TARGET_LOG
```

实测（2026-09-30，真 U 盘 + 25 GiB 靶盘）：靶盘（ESP 512MiB + 单 root 24.5 GiB）装完 Ubuntu 22.04.4 →
`verify_target_image.sh` 全绿（需 `VTOY_AI_TARGET_MIN_ROOT_MIB=24000` 覆盖默认阈值）→ `run_qemu_target.sh`
引导进入 `gdm3` 桌面 ⇒ 修前的「grub-install 报 unknown filesystem / 装完无 initrd」两个失败模式均不再复现。

## 9) 本地模型零配置端到端（内置 llama-server + GGUF）

两条路径：**A** 只用 ISO **内置** llama-server（数据分区只放模型）；**B** 数据分区放**用户自带**
llama-server（验证二进制的用户文件优先 + exFAT 可执行性）。两盘均 exFAT、无 ai.json、同一份 2 轮问答脚本。

```sh
# 造 exFAT 数据分区镜像（宿主 mkfs.exfat，来自 exfatprogs 包；免 root 可 apt-get download + dpkg -x 提取）
D=$BUILD/test/local-llm
dd if=/dev/zero of=$D/a.img bs=1M count=3072 status=none
mkfs.exfat -L VTAIA $D/a.img
# 挂载后放 payload：/ventoy/ai/models/qwen3.5-4b-q4km.gguf + test_script.txt
# （b.img 再放 /ventoy/ai/llama-server = 自带的静态二进制，测用户覆盖路径）

VTOY_AI_QEMU_MEM=6144 sh $AI/pack/run_qemu.sh "" "" $D/a.img 420   # A：内置二进制
VTOY_AI_QEMU_MEM=6144 sh $AI/pack/run_qemu.sh "" "" $D/b.img 420   # B：用户二进制放 exFAT
```

实测（2026-10-01，x86_64 QEMU/KVM、6 GB 内存，Qwen3.5-4B-Q4_K_M 2.6 GB）：

| 判据 | A（内置） | B（用户文件） |
|------|-----------|---------------|
| 二进制来源 | payload 无 llama-server 文件 ⇒ 只能跑内置版 | 日志明证 `启动本地模型: /iso/ventoy/ai/llama-server + ...`（用户文件优先） |
| 就绪/内存 | 2 s，RSS 4.43 GB（模型 mmap 自 exFAT 直读） | 2 s，RSS 4.43 GB |
| 问答 | 2/2 轮全中文：`list_disks` 正确标出唯一盘 `protected=true` → 解释「运行盘不能动」；随后完整能力介绍 | 同左 |
| 落盘 | 会话日志写回 exFAT `/iso/ventoy/ai/logs/session-*.{jsonl,md}` | 同左 |
| 退出 | `rc=0` + `reboot: Power down`（guest 内 165 s / 159 s） | |

- **无 ai.json → 自动本地**：`未找到配置文件 … 尝试使用本地模型` → `已接入本地模型: qwen3.5-4b-q4km`，
  横幅 `模型: qwen3.5-4b-q4km（本地）`；function calling（`list_disks`）经 llama-server `--jinja` 直通。
- **exFAT 执行的关键**：`mount_payload.sh` 对 exfat/vfat 显式 `fmask=0022,dmask=0022`（exFAT 权限位由
  挂载选项合成，root 只能执行「至少有一个 x 位」的文件）；system_probe 的 mounts 里可见该挂载选项。
- 证据文件：`$BUILD/test/local-llm/{qemu-a-serial.log,qemu-b-serial.log,session-a.md,session-b.md}`。

**上下文预算回归**（2026-10-01，修复"本地模型 HTTP 400 exceed_context_size_error"）

真实 U 盘塞了 210 个文件（成套软件目录上百个 DLL 路径）时，`system_probe` 单独占 7,321 token，
叠加系统提示与 11 个工具定义（3,298 token）达 10,615 token，`-c 8192` 直接被 llama-server 拒为
HTTP 400。复现盘的造法：

```sh
D=$BUILD/test/local-llm
cp --reflink=auto $D/a.img $D/a5.img        # 复用带模型的 exFAT 盘
timeout 30 udisksctl loop-setup -f $D/a5.img
LP=$(losetup -j $D/a5.img | cut -d: -f1); timeout 30 udisksctl mount -b $LP

# 按修复前抓到的 system_probe 清单还原文件树（大小一律 4 KiB：token 只取决于路径）。
# 过滤条件必须跳过 models/*.gguf 与 logs/* —— exFAT 大小写不敏感，按清单 truncate
# 会把 2.7 GB 的模型文件压成 4 KiB，guest 里表现为"模型加载失败"（已踩过）。
LIST=<修复前抓到的探测 JSON>   # 形如 {"payload":{"files":[{"path":...,"size":...}]}}
python3 -c '
import json, os, sys
root = sys.argv[1]
for f in json.load(open(sys.argv[2]))["payload"]["files"]:
    p = f["path"]
    if "/models/" in p.lower() or "/logs/" in p.lower():
        continue
    t = os.path.join(root, p.lstrip("/"))
    os.makedirs(os.path.dirname(t), exist_ok=True)
    open(t, "wb").truncate(4096)
' /media/wmx/VTAIA "$LIST"

timeout 30 udisksctl unmount -b $LP; timeout 30 udisksctl loop-delete -b $LP
VTOY_AI_QEMU_MEM=6144 sh $AI/pack/run_qemu.sh "" "" $D/a5.img 420   # 16384 档
VTOY_AI_QEMU_MEM=4096 sh $AI/pack/run_qemu.sh "" "" $D/a5.img 420   # 8192 档（见下方内存下限）
```

| 判据 | 修复前 | 修复后 |
|------|--------|--------|
| guest 内 `system_probe` | 18,434 B / 7,321 tok（files 列 200 项） | 5,586 B / 2,370 tok（files 60 项 + images 5 项 + `files_truncated`） |
| 首轮 prompt | 10,615 tok ⇒ **HTTP 400** | 5,676 tok（连 8192 档都余 2.5k） |
| 模型再调 system_probe | 同一份 JSON 再进一次（+5,974 tok） | 32 tok 指针说明，环境变了才回完整结果 |
| 分档落地 | 恒 `-c 8192` | `-m 4096`→`上下文窗口: 8192（本机内存 3910 MB）`；`-m 6144`→`16384（5920 MB）` |
| 端到端 | 400 中断 | 0 次 400，2/2 轮答完，`rc=0` + `Power down`（226 s） |

- 模型看到 `files_truncated` 提示后**自己**改用 `run_command` 取了完整清单（串口日志可见
  "我来查看完整的文件清单"→ 列出镜像），说明截断没有牺牲可用性。
- 内存下限：`-m 4096` 下模型加载即失败（`llama_model_loader: failed to load model`），
  与预算修复无关，属 4B-Q4 的固有门槛；故 8192 档主要在换小模型或远程服务时生效。
- 证据文件：`$D/qemu-serial.log`（16384 档全链路）、`/tmp/a4.log`（8192 档分档日志）。

**降级分支**（同日实测，均干净退出 rc=2 + `Power down`，~11s）：

```sh
# C1：数据分区只有 /ventoy（无模型）——init 提示下载、agent 报可操作的配置错误
VTOY_AI_QEMU_MEM=6144 sh $AI/pack/run_qemu.sh "" "" $D/c.img 180
# C2：有模型但 CPU 无 AVX2（-cpu Nehalem）——内置版不启动并提示换 v2
VTOY_AI_QEMU_ACCEL='-accel kvm -cpu Nehalem' VTOY_AI_QEMU_MEM=6144 sh $AI/pack/run_qemu.sh "" "" $D/a.img 180
```

- C1：`未找到模型 /iso/ventoy/ai/models/*.gguf，跳过本地模型` → `可运行 tools/fetch_local_llm.sh`
  → agent `配置错误: base_url 未配置…`（证据 `c1-no-model.log`）。
- C2：`本机 CPU 不支持 AVX2，内置 llama-server 无法运行；可从 GitHub Release 下载 llama-server.v2`
  → agent 同样给出配置错误（证据 `c2-noavx.log`）。
